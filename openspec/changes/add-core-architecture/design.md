# Design: Core Architecture

## Context

poxo is a pure Python DataFrame library grounded in category theory. The
architecture draws from Spivak's functorial data migration, Clojure transducers,
and the observation that `reduce` is the universal operation on data (catamorphism
on initial F-algebra).

The library must serve two modes:
- **Exploration** (Jupyter, REPL): inferred schemas, quick iteration, `head()` previews
- **Production** (VS Code, scripts): declared schemas, static type checking, strict validation

## Goals / Non-Goals

Goals:
- Two primitives: `reduce` (row-wise catamorphism) and `project` (schema-wise Δ)
- All other operations (filter, map, groupby, join, sort) compose from these
- Single lazy DataFrame type — always lazy, display triggers collection
- Clean pipe syntax via `|` operator
- Schema as dataclass with descriptor-based `Expr` on class access
- Pipeline steps as product category: (data transform, schema transform)
- Swappable Storage and Compute backends via protocols (future change, not in this proposal)

Non-Goals:
- Feature parity with pandas
- Performance optimization (first make it correct, then make it fast)
- NumPy backend (future adapter, not in this change)
- HAMT / persistent data structures (future, pending performance evaluation)

## Capability Boundaries

The proposal is intentionally split into narrowly scoped OpenSpec capabilities
so the specification dependency graph remains a DAG instead of collapsing into
a single monolith.

Dependency direction (`A → B` means "B depends on A"):

`row-model → expression → aggregation → relational`

`schema → expression`

`reducer → transducer → pipeline`

`pipeline → dataframe`

`aggregation → relational`

`pipeline → relational`

Boundary rules:
- `row-model` owns the shape of a materialized row and nothing else
- `expression` depends on `row-model` and `schema`, but not on `dataframe`
- `reducer` owns fold laws and built-in reducers, but not schema-aware
  column extraction
- `aggregation` owns Expr-bound reducers such as `sum_of(expr)`
- `pipeline` owns `PipelineStep`, `SchemaTransform`, and pipeline-step
  factories such as `where`, `select`, `derive`, `sort_by`, and `distinct`
- `dataframe` owns the `DataFrame` facade: construction, laziness,
  materialization triggers, exports, and `DataFrame | step`
- `relational` owns `groupby` and `join`, including result-schema rules

Allowed normative references:
- `expression` MAY reference `row-model` and `schema`
- `transducer` MAY reference `reducer`
- `pipeline` MAY reference `expression`, `transducer`, and `dataframe`
- `dataframe` MAY reference `pipeline`, `aggregation`, `schema`, and `row-model`
- `relational` MAY reference `pipeline`, `aggregation`, `expression`, and `dataframe`

This lets each capability change for one reason and reduces co-change across
the spec set.

## Decisions

### Single lazy DataFrame — no LazyFrame

There is only `DataFrame`. It is always lazy — it holds a **plan** (a list of
pipeline steps) and a **data source** (dict of lists, or another DataFrame's
plan). The plan IS the value.

```python
df = po.DataFrame({"name": ["Ana", "Luis"], "age": [30, 25]})  # plan: []
filtered = df | po.where(Person.age > 25)  # plan: [where(age > 25)]
result = filtered | po.select(Person.name)  # plan: [where(age > 25), select(name)]
```

**Materialization triggers** (force evaluation of the plan):
- `repr(df)` / `_repr_html_(df)` — display in REPL/Jupyter
- `for row in df` — iteration
- `len(df)` — row count
- `df.collect()` — explicit force, returns a new materialized DataFrame

DataFrame is a fully immutable value object — no internal caching. Each
materialization trigger re-executes the plan. `collect()` returns a *new*
DataFrame with data inline and an empty plan. This preserves referential
transparency: observation never changes state.

**Why no LazyFrame**: A separate LazyFrame type breaks the pipeline endomorphism.
`DataFrame | xf → DataFrame` is a clean endomorphism. With LazyFrame, the first
`|` changes type, requiring `.collect()` to get back — monadic context leakage.
One type, always lazy, is simpler and composes cleanly.

**Why lazy matters for learning**: Pandas applies operations eagerly, making
optimization impossible after the fact. poxo keeps the plan visible and
composable, teaching users that data pipelines are recipes, not results. The
`repr` auto-collecting for display means exploration feels immediate while the
underlying model remains lazy.

### Schema system: `@po.schema` decorator with field descriptors

`@po.schema` wraps `@dataclass` and replaces fields with `ColumnDescriptor`s.
Class access (`Person.age`) returns an `Expr` node. Instance access (`p.age`)
returns the value. This gives ergonomic column references without magic proxies.

Implementation note: `@po.schema` must apply `@dataclass` first, then layer
descriptors carefully so that `dataclasses.fields()` still returns correct
metadata. The `__init__` generated by `@dataclass` must not be intercepted.
Instance `__eq__` must use the dataclass-generated `__eq__` (returns `bool`),
not `Expr.__eq__`.

Alternatives considered:
- `_` proxy (siuba-style): rejected — confusing, no IDE support for column names
- String-based (`col("age")`): rejected — no autocomplete, error-prone
- Plain dataclass + separate `col()` wrapper: workable but less ergonomic

### Expression tree: `Expr` with operator overloading

`Expr` represents a deferred computation. Built via descriptors and operators:
- `Person.age` → `ColumnRef("age", dtype=int)`
- `Person.age > 30` → `BinOp(GT, ColumnRef("age"), Literal(30))`
- `Person.age + 1` → `BinOp(ADD, ColumnRef("age"), Literal(1))`

For joins, the project intentionally narrows the supported predicate language
to conjunctions of **column-reference equalities** only. In
`LeftSchema.col == RightSchema.col`, the left ColumnRef is evaluated against
the left row and the right ColumnRef against the right row. Computed
expressions in join predicates are rejected with a `TypeError`. This avoids
inventing a separate two-table expression hierarchy while keeping join
semantics simple and unambiguous for a teaching library.

`Expr` implements:
- Comparison: `__gt__`, `__lt__`, `__ge__`, `__le__`, `__eq__`, `__ne__`
- Arithmetic: `__add__`, `__sub__`, `__mul__`, `__truediv__`
- Reverse arithmetic: `__radd__`, `__rsub__`, `__rmul__`, `__rtruediv__`
- Boolean: `__and__`, `__or__`, `__invert__`

**`__eq__` trade-off**: `Expr.__eq__` returns an `Expr` (not `bool`), enabling
`Person.age == 30` as a query expression. This breaks normal Python equality
semantics. Because `__eq__` does not return `bool`, `Expr` is explicitly
unhashable (`__hash__ = None`). Any collections of Expr-related data (like
`required_columns`) MUST store column names (strings), not `Expr` instances.
A separate `.equals(other)` method returns `bool` for structural Expr comparison.

**`|` operator disambiguation**: `Expr.__or__` is used for boolean OR between
expressions (`(age < 18) | (age > 65)`). `Transducer.__or__` is used for
pipeline composition. These don't conflict because Python dispatches `|` based
on operand types — `Expr | Expr` goes to `Expr.__or__`, and
`Transducer | Transducer` goes to `Transducer.__or__`. The pipe `DataFrame | Transducer`
goes to `DataFrame.__or__`.

**Expr evaluation is a homomorphism**: Evaluating an Expr against a row is a
structure-preserving map from the free algebra to Python values:
`eval(combine(e1, e2), row) == combine(eval(e1, row), eval(e2, row))`.
This is verified via PBT.

### Three-phase reducer protocol (Clojure-style)

A reducer has three phases:
- `init() -> Acc` — produce initial accumulator
- `step(acc: Acc, item: Row) -> Acc | Reduced[Acc]` — incorporate one item
- `complete(acc: Acc) -> Result` — finalize the result

This enables reducers like `mean` that accumulate `(sum, count)` and divide in
`complete`. The three-phase protocol is what makes transducers composable.

**Early termination**: `step` can return `Reduced(acc)` to signal that iteration
should stop (e.g., `taking(n)` after n items). The `reduce` driver checks for
`Reduced` after each step and proceeds to `complete` if found.

**Algebraic structure**: A Reducer is a **Moore machine** (left fold with
finalization). The `step` function is a left monoid action on the accumulator.

**Reducer laws**:
1. **Determinism**: `step(s, a)` always produces the same result for same `s`, `a`
2. **Empty input**: `complete(init())` produces a valid, well-defined result
3. **Resumability**: reducing `xs ++ ys` equals resuming the fold of `ys` from
   the accumulated state after `xs` (for non-`Reduced` cases)
4. **Reduced validity**: if `step` returns `Reduced(s)`, `complete(s)` is valid
5. **Reduced idempotence**: `Reduced(Reduced(s))` is treated as `Reduced(s)`

**Transducer-reducer compatibility laws**:
1. **Init preservation**: `xf(r).init() == r.init()` (default; transducers may override)
2. **Complete propagation**: `xf(r).complete(s)` must call `r.complete(...)` on some state
3. **Reduced propagation**: if inner `step` returns `Reduced`, outer must propagate it

### Transducers as reducer transformers

A transducer transforms a reducer into another reducer:
`Transducer = Reducer -> Reducer`

This is the formalization of Hickey's insight that map, filter, take, etc. are
all special cases of reduce. A transducer is a natural transformation between
fold functors, polymorphic in the accumulator type.

**Composition is left-to-right**: `xf1 | xf2` means apply xf1 first, then xf2
in data flow order. `comp(first=xf1, second=xf2)` is the same as `xf1 | xf2`.

Internally, left-to-right data flow requires right-to-left function composition:
`(xf1 | xf2)(reducer) == xf1(xf2(reducer))`. The outermost wrapper (xf1) gets
called first for each item, then passes to xf2's wrapper.

**Why left-to-right**: This is a teaching library. `a | b | c` should read as
"first a, then b, then c" — matching the visual order. We break with Clojure's
`comp` convention (which uses mathematical right-to-left composition) to avoid
a well-known footgun. Named parameters (`first=`, `second=`) make the order
unambiguous.

**Transducer composition laws** (verified via PBT):
1. **Identity**: `identity | xf == xf == xf | identity`
2. **Associativity**: `(xf1 | xf2) | xf3 == xf1 | (xf2 | xf3)`

Use non-commutative transducers in PBT (e.g., `mapping(x-3) | filtering(x>0)`)
to ensure associativity is tested meaningfully.

**Identity transducer**: `comp()` with no arguments returns the identity
transducer. This completes the monoid structure.

### Pipeline steps as product category

A pipeline step is a pair `(data_op, schema_transform)`:

```python
PipelineStep = (data: DataOp, schema: SchemaTransform)
```

`DataOp` is either:
- `StreamingOp` — backed by a transducer (processes rows one at a time)
- `MaterializingOp` — requires all input rows before producing output

- `where(expr)`: data=StreamingOp(filtering by expr), schema=identity
- `select(*cols)`: data=StreamingOp(column dropper), schema=projection
- `sort_by(*exprs)`: data=MaterializingOp(sort), schema=identity
- `groupby(...)`: data=MaterializingOp(group-aggregate), schema=GroupBy

Composition is component-wise:
```
(d1, s1) | (d2, s2) = (d1 | d2, s1 ∘ s2)
```

When composing, if either data component is materializing, the result is
materializing (the collection boundary is preserved).

Both components compose independently in their own category:
- Data ops: streaming ops compose via transducer monoid; materializing ops
  create collection boundaries
- Schema transforms: function composition (associative, has identity)

**Why a product category**: `select` does two things — transforms rows AND
transforms schema. Mixing them in one transducer is conflation. The product
makes each concern explicit:
- Schema transforms can be composed and analyzed without touching data
- Data transforms don't carry schema metadata as side-channels
- The type checker can track schema evolution through the pipeline
- Pure schema transforms (rename, reorder) can be optimized to zero data cost

**SchemaTransform operations** (this change):
- `Identity` — no schema change
- `Project(columns)` — keep only named columns
- `GroupBy(keys, aggregations)` — group key columns + aggregation result columns
- `Extend(new_columns)` — add computed columns (for `derive`)

**SchemaTransform operations** (deferred to future changes):
- `Rename(mapping)` — rename columns

### Materializing pipeline steps

Most pipeline steps are **streaming**: their data component is a transducer that
processes rows one at a time (`where`, `select`, `distinct`). Some steps are
**materializing**: they require all input rows before producing output (`sort_by`,
`groupby`).

A materializing step acts as a collection boundary within the pipeline. The
pipeline executor collects all rows up to the materializing step, applies the
transform, and continues with the result. Schema transforms work identically
for both kinds — the streaming/materializing distinction applies only to the
data component.

Composition involving materializing steps: when a materializing step is composed
with any other step via `|`, the result is a materializing step (the boundary
must be preserved).

### API layering: low-level and high-level

Two layers of transducer API:

**Low-level** (work with plain Python callables):
- `filtering(predicate)` — `predicate` is `item -> bool`
- `mapping(function)` — `function` is `item -> item`
- `taking(n)`, `dropping(n)`
- `comp(first=xf1, second=xf2)` — compose transducers, left-to-right
- These are public API for advanced users building custom transducers.

**High-level** (work with `Expr` objects, user-facing):
- `where(expr)` — wraps `filtering` with Expr evaluation per row
- `select(*column_refs)` — project operation from ColumnRef expressions only
- `derive(**named_exprs)` — add computed columns from Expr evaluation
- `sort_by(*exprs, descending=)` — reorder rows (materializing step)
- `distinct(*exprs)` — remove duplicate rows

`where(Person.age > 25)` internally builds a pipeline step:
`(data=filtering(lambda row: evaluate(expr, row)), schema=Identity)`.

`select(Person.name)` internally builds:
`(data=column_dropper(["name"]), schema=Project(["name"]))`.

`derive(bonus=Person.salary * 0.1)` internally builds:
`(data=row_extender({"bonus": expr}), schema=Extend({"bonus": float}))`.

### Two primitives: reduce + project

- `reduce`: universal row-wise operation (catamorphism). Implemented as the
  data component of pipeline steps.
- `project`: universal schema-wise operation (Δ). Implemented as the schema
  component of pipeline steps.

Both are unified in the product category — every pipeline step has both a
reduce part and a project part, with identity as default for whichever is
not needed.

### Pipe operator via `__or__`

- `DataFrame.__or__(step)` → new `DataFrame` (plan extended, endomorphism)
- `PipelineStep.__or__(step)` → composed `PipelineStep`
- `PipelineStep.__call__(df)` → `(df | self)` (convenience, returns lazy DataFrame)

Pipelines are first-class: `pipeline = where(...) | select(...)` is a
composed pipeline step, reusable across DataFrames.

### Schema inference and `to_code()` bridge

For exploration, schema is inferred from data:
```python
df = po.DataFrame({"name": ["Ana"], "age": [30]})
S = df.schema  # auto-generated schema with descriptors
df | po.where(S.age > 25)  # works in Jupyter/REPL (dynamic autocomplete)
```

`df.schema.to_code()` prints the `@po.schema` class definition, bridging
exploration into production code.

### Schema evolution is auto-generated

Operations that change the schema (project, derive) produce DataFrames with
auto-generated schemas. In production, you can optionally declare the target
schema for type checking.

### User-facing reduce

`po.reduce(reducer, df)` applies a reducer directly to a DataFrame's rows.
Optional `transducer` parameter applies a transducer to the reducer first.
This forces collection and returns a scalar result.
Scalar column reductions on DataFrames use column-bound reducers such as
`sum_of(Person.age)` because DataFrame iteration yields row dicts, not raw
column values. The optional `transducer=` hook is restricted to streaming
wrappers; materializing pipeline steps like `sort_by` are not valid reducer
wrappers.

## Module Structure

All public API SHALL be importable via `from poco import po`. Internal
implementation uses submodules with leading underscore, re-exported through
`poco/po.py`:
- `poco/_expr.py` — Expr, ColumnRef, Literal, BinOp, UnaryOp, required_columns, result type inference
- `poco/_schema.py` — schema decorator, ColumnDescriptor, inference
- `poco/_reduce.py` — Reducer protocol, Reduced, reduce(), built-in reducers
- `poco/_transducer.py` — Transducer protocol, filtering, mapping, taking, dropping, comp
- `poco/_pipeline.py` — PipelineStep, SchemaTransform, where, select, groupby
- `poco/_dataframe.py` — DataFrame
- `poco/_join.py` — join operation
- `poco/_errors.py` — SchemaError, ColumnNotFoundError, NullValueError

### DataFrame[Schema] generics

`DataFrame` implements `__class_getitem__` to accept a schema type parameter.
`DataFrame[Person]` is equivalent to `DataFrame` at runtime — the parameter
is for type checker hints only.

## Public API Surface

```python
from poco import po

# Schema
po.schema          # decorator (implies @dataclass)

# DataFrame
po.DataFrame        # constructor (from dict or rows, optional schema=)
# methods: .collect(), .head(n), .explain(), .to_dict(), .to_rows()
# properties: .schema, .columns

# High-level operations (Expr-based, produce PipelineSteps)
po.where(expr)      # filtering step (schema=identity)
po.select(*column_refs)  # project step, ColumnRef only (schema=projection)
po.derive(**exprs)  # add columns step (schema=extend)
po.sort_by(*exprs, descending=)  # ordering step (materializing, schema=identity)
po.distinct(*exprs) # dedup step (schema=identity)
po.groupby(*keys, **aggs)  # group-aggregate step (schema=GroupBy)
po.join(left, right, on=, how=, suffixes=)  # relational join (returns lazy DataFrame)

# Low-level transducers (callable-based)
po.filtering(pred)  # filter transducer
po.mapping(fn)      # map transducer
po.taking(n)        # take-n transducer (early termination)
po.dropping(n)      # drop-n transducer
po.comp(first=, second=)  # compose left-to-right (identity if no args)

# Reduce
po.reduce(reducer, df, transducer=None)  # apply reducer, forces collection

# Built-in reducers
po.to_list          # collect all items into a list
po.count            # count items (0 on empty)
po.sum_reducer      # sum items (0 on empty)
po.mean             # arithmetic mean (ValueError on empty)
po.min_reducer      # minimum (ValueError on empty)
po.max_reducer      # maximum (ValueError on empty)

# Column-bound reducers (for groupby aggregations)
po.sum_of(expr)     # extract column, sum values
po.mean_of(expr)    # extract column, compute mean
po.min_of(expr)     # extract column, find minimum
po.max_of(expr)     # extract column, find maximum
po.count_of()       # count rows

# Classes / types (for type hints and isinstance checks)
po.Expr             # expression base type
# methods: .equals(other), .is_null(), .fill_null(default)
# properties: .required_columns, .result_type
po.Reducer          # reducer protocol
po.Transducer       # transducer protocol
po.PipelineStep     # (data_op, schema_transform) pair
po.DataOp           # data operation (StreamingOp | MaterializingOp)
po.SchemaTransform  # schema transformation (Identity, Project, GroupBy, Extend)
po.Reduced          # early termination sentinel
po.SchemaError      # schema validation error
po.ColumnNotFoundError  # missing column error
po.NullValueError   # null in strict operation
```

## Risks / Trade-offs

- **Descriptor magic**: `@po.schema` replaces dataclass field access at class
  level. This is well-understood Python (descriptors are how `property` works)
  but may surprise users unfamiliar with the protocol.
  Mitigation: clear docs, error messages that explain what happened.

- **`__eq__` override**: `Expr.__eq__` returns Expr, not bool. This is a known
  Python footgun (breaks `assert expr == expected`, `in` checks, etc.).
  Mitigation: `.equals()` method, `__hash__` consistency, documentation.

- **Implicit collection**: `repr(df)` triggers materialization. Users may not
  realize display has a cost. Each `repr` re-executes the plan (no caching).
  Mitigation: display shows the plan steps before the data table, making the
  lazy→eager transition visible. For expensive pipelines, users call
  `df2 = df.collect()` once and work with the materialized `df2`.

- **No caching trade-off**: Re-executing the plan on each `repr`/`iter`/`len`
  is intentional — DataFrame is a true immutable value object with no hidden
  mutable state. For a teaching library working with small-to-medium data,
  re-computation cost is negligible. Users who need to avoid re-computation
  use `collect()` to produce a new materialized DataFrame.

- **Breaking with Clojure comp**: `comp(first=a, second=b)` is left-to-right,
  not mathematical composition. This is intentional for a teaching library but
  may confuse users coming from Clojure/Haskell. Mitigation: named parameters
  make the order unambiguous.

## Open Questions

- `sort_by` implementation strategy: materializing steps require a collection
  boundary within the pipeline executor. Need to decide whether the executor
  uses an explicit `Materializer` type or handles this via dynamic dispatch on
  the pipeline step's data component.
- Derived column type inference: `derive(bonus=Person.salary * 0.1)` needs to
  infer that `bonus` is `float`. For arithmetic on typed columns this is
  straightforward, but complex expressions (conditionals, null coalescing) may
  need explicit type annotation.
